# Obsidian Analytics Web App

## 1. Обзор проекта

Данный проект представляет собой локальное веб-приложение для анализа, визуализации и управления данными из базы знаний Obsidian.

Система парсит структурированные заметки (Markdown + YAML frontmatter), извлекает данные, сохраняет их в локальную базу данных и отображает через веб-интерфейс. 

**Принципы работы с данными:**
*   **Source of Truth:** Единственным источником истины является заметка в Obsidian. Данные в БД всегда актуализируются на основе содержимого файлов.
*   **Редактирование:** Изменение данных (оценок, дат, статусов) происходит только внутри Obsidian. Сайт считывает эти изменения при синхронизации.
*   **Создание:** Создание новых заметок идет только внутри Obsidian.

## 3. Архитектура системы

### 3.1 Синхронизация
*   **Инициация:** Обновление данных в БД запускается **только вручную через веб-интерфейс** в одном конкретном модуле.
*   **Валидация и Логирование:** 
    *   При парсинге проверяется наличие обязательных полей.
    *   Все ошибки (битый YAML, отсутствие данных, неверный формат) записываются в `logs\`.
    *   Файлы с критическими ошибками пропускаются, чтобы не засорять БД некорректными данными.
*   **Результат:** По завершении синхронизации в окне на сайте выводится **статистика**: сколько файлов обработано, сколько обновлено, сколько пропущено из-за ошибок.

### 3.2 ETL-система (Parser)
Процесс разделен на три независимых слоя:
1.  **Engine (Scanner):** Низкоуровневый обход директорий. Возвращает метаданные файлов (пути, даты изменения).
2.  **Transformers:** Набор специализированных классов для каждого модуля. Преобразуют сырой Markdown/YAML в объекты SQLModel.
3.  **Sync (Orchestrator):** Логика синхронизации. Сопоставляет данные сканера с БД, принимает решение об обновлении, вызывает трансформеры и обрабатывает ошибки.

### 3.3 Слой доступа к данным
1.  **Repository:** Инкапсулирует все запросы к SQLite. Отвечает за CRUD операции.
2.  **Service:** Реализует бизнес-сценарии (генерация файлов, подготовка сложных отчетов, фильтрация).

### 3.4 База данных
*   **SQLite + SQLModel:** Каждому модулю соответствует своя таблица с четкой схемой данных.

### 3.5 Веб-приложение
*   **FastAPI + HTMX:** Обеспечивает интерактивность (динамические графики, индикаторы загрузки при синхронизации) без перезагрузки страниц.

## 5. Технологический стек

### Backend / Parsing
*   **FastAPI** — основной веб-фреймворк для построения API и маршрутизации.
*   **SQLModel (SQLAlchemy + Pydantic)** — ORM для работы с базой данных SQLite, объединяющая валидацию типов и работу с SQL.
*   **python-frontmatter** — основной инструмент для извлечения YAML-метаданных и Markdown-контента из заметок Obsidian.
*   **Loguru** — продвинутое логирование всех этапов синхронизации с разделением логов по сессиям и уровням важности.
*   **Pydantic Settings** — управление конфигурациями приложения через переменные окружения и `.env` файлы.
*   **SQLite** — быстрая и надежная база данных, не требующая отдельного сервера.

### Frontend
*   **Jinja2** — шаблонизатор для динамического рендеринга HTML на стороне сервера.
*   **HTMX** — обеспечение "бесшовной" интерактивности (поиск, фильтрация, синхронизация) без полной перезагрузки страниц.
*   **Vanilla CSS** — кастомная дизайн-система, построенная на современных CSS-переменных (Custom Properties) и Flexbox/Grid.
*   **Chart.js** — библиотека для визуализации данных (радарные диаграммы в модулях книг/игр и будущие графики в дневнике).
*   **Google Fonts (Inter)** — типографика интерфейса.

## 6. Поток данных

1.  **Синхронизация (ETL):** 
    `Obsidian (.md)` ⮕ `ScannerEngine` (поиск измененных файлов) ⮕ `Module Transformer` (парсинг YAML и Regex-валидация) ⮕ `Repository` (Upsert в базу данных) ⮕ `SQLite`.
2.  **Обработка и Агрегация:** 
    `SQLite` ⮕ `SQLModel` (выборка данных) ⮕ `Service Layer` (расчет ISO-недель, средних показателей сна/веса и суммирование времени активностей) ⮕ `View Context`.
3.  **Отображение и Интерактив:** 
    `FastAPI` ⮕ `Jinja2 Template` (рендеринг страниц и макросов) ⮕ `HTMX` (частичное обновление списков и отчетов синхронизации) ⮕ `UI`.
4.  **Визуализация:** 
    `Database Stats` ⮕ `Chart.js` (отрисовка радарных диаграмм и графиков активности на стороне клиента).

## 8. Описание модулей и особенности реализации

### 📚 Модуль «Книги» (Books)
Центральный модуль для глубокого анализа прочитанного контента.
*   **Особенности парсинга:**
    *   **Extended YAML:** Используется расширенный набор метаданных, включая 10 параметров личного рейтинга (сюжет, герои, слог и т.д.).
    *   **Read Log:** Сложный парсинг строки лога чтения (`||` как разделитель сессий). Система автоматически определяет тип контента (аудиокнига по наличию `:` в объеме или тега `audio`).
    *   **Smart Covers:** Автоматический поиск обложек в папке `files/covers/books/` по названию заметки.
*   **Уникальные фичи:**
    *   **Расчет темпа:** На детальной странице вычисляется средний темп чтения (стр/день) для каждой сессии.

### 🎮 Модуль «Игры» (Games)
Модуль для трекинга игрового опыта с интеграцией внешних метрик.
*   **Особенности парсинга:**
    *   **Play Log:** Парсинг игровых сессий с поддержкой "флага завершения" сюжетной линии (символ `!` в комментарии лога).
    *   **External IDs:** Внешние рейтинговые показатели Steam, Metacritic, ID игры с сайта IGDB.
*   **Уникальные фичи:**
    *   **Perfect Badge:** Игры, пройденные на 100% достижений, получают золотую иконку кубка и особую подсветку в списке.
    *   **Аналитика бэклога:** Расчет времени от покупки (из YAML) до первого запуска и до финала сюжета.
    *   **Progress Tracking:** Визуальная шкала прохождения на основе данных `hours_played` и эталонного времени с HLTB (`hours_to_beat`).
    *   **Watched games:** Поддерживается статус Watched, который символизирует только просмотрение игры на каком-то канале, личного прохождения не было.

### 📅 Модуль «Дневник» (Daily) — *Ключевой модуль аналитики*
Сложная система сбора ежедневных показателей и хронометража.
*   **Особенности парсинга (Strict Regex):**
    *   **Игнорирование эмодзи:** Поиск разделов (Сон, Здоровье, Время) ведется по ключевым словам в заголовках `##`, что делает парсер устойчивым к смене иконок.
    *   **Жесткая валидация:** Если в заметке есть заголовок «Личные показатели», система требует заполнения всех 5 параметров (вес, ИМТ, жир, мышцы, висцеральный жир), иначе файл помечается ошибкой.
    *   **Time Tracking:** Парсинг строк формата `- Сервис (Уточнение | Тип) - Время`. Время (например, `1h 20m`) автоматически конвертируется в минуты для хранения в БД.
*   **Уникальные фичи:**
    *   **Двухнедельный Хаб:** Вместо бесконечного списка на главной странице модуля отображается текущая и прошлая недели (сетка 14 дней).
    *   **Раздельный сон:** Система отдельно считает и выводит средние показатели для ночного сна (с учетом перехода через полночь) и дневного сна (naps).
    *   **Интерактивный календарь-архив:** Боковая панель со сворачиваемыми годами и месяцами для быстрого доступа к любой дате за десятилетия.
    *   **Безопасность данных:** Текущий день автоматически пропускается при синхронизации, чтобы в базу не попадали неполные данные до завершения суток.

### 🛠 Общие технические решения

*   **Модульная синхронизация:** Каждый модуль имеет свой `Transformer`, что позволяет изолированно менять логику парсинга книг или дневников, не затрагивая остальную систему.
*   **HTMX-интерактивность:** Синхронизация данных и поиск работают без перезагрузки страницы, предоставляя мгновенную обратную связь через `sync_report`.
*   **Repository Pattern:** Вся работа с базой данных инкапсулирована в репозиториях, что гарантирует чистоту данных и простоту каскадных удалений (например, при удалении дня удаляются все связанные логи времени).
*   **Красивые логи:** В терминал выводится идеально выровненная таблица данных каждого обработанного объекта (книги/игры), что упрощает визуальный контроль процесса синхронизации.
